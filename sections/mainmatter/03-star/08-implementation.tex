We now describe the implementation of the protocol given in \cref{fig:protocol_report}.
We instantiate the linearly homomorphic encryption scheme with dense ciphertext space required by $\pdope$ with the Benaloh encryption scheme described in \cref{sec:benaloh_scheme}.
We implement all algorithms in CUDA C$++$ using the NTL \cite{ntl} library.
We additionally make a number of optimizations to the $\chmdss_\np.\reconstruct$ algorithm, which we describe below.
All code can be seen at \repourl{}.

\subsection{Optimizing Aggregation}
\label{sec:star-optimizations}

While the MDSS implementation of $\chmdss$ from \cite{\citeairtag} aggregates efficiently for up to $3150$ shares, it does not scale well for the parameters required by this setting, in which it may be run on sets of $100{,}000$ or more.
Indeed, using the implementation from \cite{\citeairtag}, aggregating from $50{,}000$ shares takes over two hours \emph{per recovered secret}, resulting in a $17$ hour runtime.
Here we first describe the inner-workings of the $\chmdss$ algorithm, and then the optimizations we make to improve the aggregation runtime.

\subsubsection{Algorithm Overview}
\label{sec:algorithm-overview}
Recall from \cref{sec:chmdss} that $\chmdss.\mdssReconstructAlg$ takes a set of $\mdssWindowSize$ shares as input and outputs the secrets corresponding to  values with over $\threshold$ shares.
In our MDSS construction each share is a tuple of field elements $(x, y_1, y_2, \dots, y_\np)$.

The $\chmdss.\mdssReconstructAlg$ algorithm first uses the set of shares to construct a $(c + 1) \times (c + 1)$ matrix, where each entry is a polynomial of max degree $\mdssWindowSize$.
It then puts the matrix into weak Popov form \cite{popov1972invariant}, using the algorithm described in \cite{mulders2003lattice}.
The \cite{mulders2003lattice} algorithm proceeds by iteratively performing elementary row operations (EROs) on the matrix, i.e.\ multiplying a row by a monomial $\polycoeff x^d$ and adding the result to another row.

Once the matrix is in Popov form, $\chmdss.\mdssReconstructAlg$ extracts the shortest vector from the matrix and performs a few simple checks on it.
If the checks pass then the algorithm uses the vector to compute the dealer polynomials $(p_1,\dots,p_{\np})$, from which a secret can be recovered, and if the checks fail the algorithm terminates.
If a secret is recovered $\chmdss.\mdssReconstructAlg$ removes all shares that agree with the recovered polynomials $(p_1,\dots,p_{\np})$ and then repeats, attempting to reconstruct a secret from the remaining $\mdssWindowSize' < \mdssWindowSize$ points.
We refer to a single iteration: building the matrix, computing the Popov form, and attempting to reconstruct the secret, as a \emph{step} of the algorithm.
Each step recovers a single heavy-hitter.
A full description of a step is shown in \cref{fig:chmdss-step}.

The vast majority of the $\chmdss.\mdssReconstructAlg$ runtime is spent putting the matrix in Popov form.
Indeed, for the $17$ hour aggregation mentioned at the start of this section, over $97\%$ of the total runtime was spent in this stage of the computation.
We therefore focus our optimizations on speeding up the Popov form step.
The first optimization accelerates the computation of the EROs, while the second allows us to compute over smaller matrices.


\subsubsection{Parallelizing EROs}

While the Popov form algorithm in \cite{mulders2003lattice} is fundamentally iterative, each individual ERO computed by the algorithm has the potential to be significantly sped up via parallelization.
If we represent each polynomial as a vector of coefficients $p = (\polycoeff_1, \dots, \polycoeff_{\max})$, then the matrix can be represented as a 3D array $M \in \field^{(\np + 1) \times (\np + 1) \times \max}$, where $M[i, j, k]$ contains the $k$'th coefficient of the polynomial at row $i$ and column $j$.\footnote{The algorithm of \cite{mulders2003lattice} never computes a matrix entry with degree greater than the largest polynomial degree in the initial matrix, which allows us to cap the representable degree at $\max$.}

Now, an ERO that sets row $\trow$ equal to itself plus row $\srow$ times a monomial $\polycoeff x^d$ can be performed by setting $M[\trow, j, k] := M[\trow, j, k] + \polycoeff \cdot M[\srow, j, k - d]$ for all $j \in [\np + 1]$ and $k \in [d, \max]$.
Note that this operation is fully parallelizable: each cell in $\trow$ can be computed independently.
This parallelizability becomes significant due to the size of our matrices.
Given that $\max \geq 50,000$, each ERO will contain millions of parallelizable operations even for modest values of $c$.

Therefore, our first optimization is to leverage the parallel processing ability of modern GPUs to speed up the Popov form computation.
This change grants a significant speedup.
As shown in \cref{fig:optimization-runtimes}, it drops the runtime on a instance with $50{,}000$ reports from $17$ hours to $44$ minutes.

\subsubsection{Optimizing for Common Input Distributions}
\label{subsubsec-distribution-optimizations}

We can further optimize our aggregation algorithm specifically for distributions that are common in the private telemetry setting.
In this setting, real-world values of interest often follow the Zipfian distribution, with popular values being heavily overrepresented in the input pool.
Indeed, it has become the standard for private telemetry algorithms to evaluate their performance and security on inputs drawn from such a distribution \cite{\citestar, \citepopstar, prio, SCN:AGJOP22}.

We begin with the observation that the algorithm described in \cref{sec:algorithm-overview} allows for different values of $c$ to be used at each step.
Practically, this means that if each report is of the form $(x, y_1, \dots, y_{\np})$, a step during aggregation could use only the first $\np' < \np$ of the $y$-coordinates instead, thereby constructing a smaller matrix and speeding up the algorithm.

Next, if we assume that the top heavy-hitters are over-represented, we can use much smaller values for $c$ in the early stages of aggregation.
As an example, for a pool of $50{,}000$ reports with $\pd = 350$, we would require a value of $c = 76$ to recover all values that are reported at least $1000$ times.
However, if we assume that our first heavy-hitter appears at least $5000$ times (an assumption that is overwhelimingly likely to be true given common Zipf parameters), we could reconstruct using $c' = 10$ during the first step, dramatically decreasing the runtime.

We can push this technique further by only reconstructing from a \emph{subset} of the total pool of reports.
Using the example from the previous paragraph, if we sample $10{,}000$ reports from the pool of $50{,}000$, then the probability that there are at least $815$ reports for the first heavy-hitter is overwhelming.
As long as the minimum number of reports is greater than $\pd$, we can set $c'$ such that recovery is guaranteed.
In this case $c' = 20$.
We refer to the size of each subset as the \emph{batch size} for the step, and denote it $\batchsize$.\footnote{We note that tuning parameters in this way does not require exact knowledge of the Zipf $\zipfexp$ parameter, but only a \emph{lower bound} on it.	Larger-than-expected values of $\zipfexp$ cause heavy-hitters to become more concentrated, and therefore increase the chance of reconstruction success.}



Our main task then is to select the size of the subsample and the value of $c'$ to use at each step of the algorithm.
We compute these by performing an exhaustive search of the possible subset sizes for each step, and selecting the configuration that ensures $\geq99\%$ chance of success while minimizing $\np \cdot \max$, an estimation of the computational cost of a given configuration.\footnote{As $\chmdss$ has only heuristic correctness it is difficult to reason formally about the runtime of the algorithm. We use $\np \cdot \max$, the size of a row of the matrix, as a reasonable proxy.}
We set the final configuration to reconstruct any value with at least $\threshold$ reports, and loop using that configuration until no value is found.

This change grants an additional speedup, bringing the runtime on an instance with $50{,}000$ reports down to $7$ minutes.
